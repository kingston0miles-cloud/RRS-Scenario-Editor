# Редактор сценариев RRS

Визуальный редактор сценариев для [Russian Railway Simulator](https://github.com/maisvendoo/RRS).
Задача: расставлять локомотивы и вагоны по карте маршрута, видеть направление путей и экспортировать
готовый сценарий (`main.lua`, конфиги составов, графики движения).

Проект отдельный от репозитория RRS, написан на C++17 и Qt6. Лицензия RRS — GPL v2; код этого
редактора пока не заимствует исходники RRS, он только читает те же файлы маршрута.

## Состояние

Этапы 20–21 — закрытие сценария без перезапуска программы и ручное построение графика:
правка времен в окне графика, закреплённые станции трассы («через станцию»), сборка
реального расписания поезда.

Что уже есть:

- чтение маршрута: траектории (`*.traj`), стрелки (`topology.xml`), станции, путевые точки;
- схема путей: масштаб колесом, перемещение левой кнопкой, поворот на 90° (клавиша `R`),
  показать всё (клавиша `F`);
- стрелки на путях показывают правильное направление пути («туда» — синие, «обратно» — оранжевые;
  серые точки — направление не определено, обычно станционные пути); см. ниже, как оно определяется;
- под курсором подсвечивается траектория, в строке состояния видны её имя и координата в метрах;
- правая кнопка копирует имя траектории в буфер обмена;
- при загрузке проверяются ссылки (стрелки и путевые точки на несуществующие траектории)
  и показываются как замечания: Вид → Замечания при загрузке.

Подвижной состав (панель справа, Вид → Подвижной состав):

- единицы из `cfg/vehicles` с длиной и массой (порожней и с грузом), признаками «локомотив» и «автоведение»;
- готовые составы из `cfg/trains` с суммарной длиной, массой и числом единиц, раскрываются в группы вагонов;
- поиск по названию;
- каталог игры определяется по маршруту (`routes/<имя>` → корень игры); если маршрут лежит вне игры,
  используется каталог из прошлого раза либо Файл → Указать каталог игры…;
- привязка единицы к модулю (какую библиотеку из `modules` загружает конфиг) выводится из готовых составов,
  при расхождениях решает каталог `modules` игры, затем самый частый вариант; если выбрать нельзя,
  единица помечается красным, и модуль назначается вручную (правая кнопка → Назначить модуль…).
  Ручные привязки сохраняются в `vehicle-modules.json` в каталоге данных программы.

Расстановка (панель «Поезда сценария» внизу):

- выберите состав или единицу в панели справа (один щелчок), затем щёлкните по пути на карте:
  под курсором виден «призрак» состава (синий — можно, красный — нельзя);
- после щелчка открывается окно подтверждения: путь, координата головы, направление головы,
  имя, флаг «Бот» (доступен, только если у крайней единицы есть автопилот);
- голова по умолчанию смотрит по направлению пути; кнопка «Развернуть» в окне меняет это;
- хвост состава прослеживается назад через стрелки, как это делает симулятор; программа не даёт
  поставить состав поверх другого или так, что хвост не умещается на путях (тупик), и предупреждает,
  если до другого поезда меньше 10 м (в игре сцепятся сами) или состав стоит через стрелку,
  положение которой по данным не определить;
- в панели поездов: «Изменить…», «Развернуть на месте» (голова переходит на место хвоста),
  «Удалить», двойной щелчок показывает поезд на карте; Esc снимает выбор состава;
- голова по умолчанию смотрит по правильному направлению пути; если выбрать обратное, окно предупредит,
  что на неправильном пути поездные светофоры по направлению не откроются.

Создание составов для `cfg/trains` (панель подвижного состава):

- «Новый состав…» (или Файл → Новый состав…, Ctrl+N): собрать состав из любых единиц и готовых составов,
  задать имя файла, название, описание, давление и «без воздуха»; сохраняется в `cfg/trains/<имя>.xml`
  игры и сразу появляется в списке и доступен для расстановки;
- правая кнопка по готовому составу: «Редактировать» (или «Сохранить копию под новым именем»);
  правая кнопка по единице: «Создать состав с …»;
- перед записью проверяются имя файла (без `/`, пробелов и т.п.), наличие единиц и известный модуль у
  каждой единицы; существующий файл заменяется только после подтверждения; поля Common, которых редактор
  не знает (`ClientName`, `TrainID` …), сохраняются.

Правка состава (кнопка «Состав…» в панели поездов):

- добавить любую единицу из каталога или готовый состав целиком, нужное число раз, в начало, конец
  или после выбранной единицы; убрать; переставить («Выше/Ниже»);
- загрузка (0–100 %) и разворот («стоит задом») для выбранных единиц;
- разбивка на несколько поездов: отметьте «Отделить перед этой единицей» — каждая часть встаёт позади
  предыдущей с зазором 15 м (больше дальности автосцепки 10 м), части получают имена «Имя (2)», «Имя (3)»;
  вагоны без локомотива просто стоят на путях;
- каждая часть проверяется: пересечения, тупик, зона сцепки; «Применить» блокируется при ошибках;
- флаг «Бот» остаётся только у головной части и только если у крайней единицы есть автопилот.

Пока нет: сохранение проекта (расстановка пропадает при закрытии) — будет вместе с экспортом сценария.

### График поезда (кнопка «График…» в панели поездов)

1. Начало пути — место поезда; конец — путевая точка из списка или щелчок по карте
   («Указать на карте…», Esc — отмена). Путь ищется по стрелкам (Дейкстра), движение против
   правильного направления путей разрешено, но невыгодно; предупреждение показывается.
2. Редактор считает ход: основное сопротивление по `MainResist` каждой единицы, уклоны (по высотам
   `.traj`), ограничения скорости из `trajectory-speedmap` (пока хвост состава не проехал ограничение —
   оно действует), торможение заранее с замедлением 0,5 м/с² (меньше реального — это запас),
   остановки на станциях. Тяга локомотивов задана в коде их модулей, поэтому берётся приближённо
   (мощность, сила тяги при трогании, скорость) и **правится вручную** в окне.
3. Станции по пути находятся по координатам из `stations.conf`. Для каждой: «в графике» (галочка),
   «Проезд» (время проезда) или «Остановка» (стоянка в минутах, не меньше минуты).
4. Запас: «на весь путь» (по умолчанию 10 %, не меньше 2 мин; распределяется по перегонам
   пропорционально времени хода) и личный «до станции» (двигает эту станцию и все следующие).
   Времена округляются вверх до минуты. Всё пересчитывается сразу после любого изменения.
5. Другие поезда: стоящий на пути поезд даёт предупреждение; у поездов с графиком сравниваются
   положения во времени (встречное движение, малый интервал) — предупреждение с временем и путём.
6. «Применить» сохраняет расписание в поезде (колонка «График» в панели, путь и станции подсвечены
   на карте). Смена положения или состава сбрасывает расписание. Запись в `timetable/*.xml` — на этапе экспорта.

### Проект и экспорт

- **Файл → Сохранить проект** (Ctrl+S, `.rrsproj`, JSON): расстановка, составы по единицам, расписания,
  имя и описание сценария, время начала. Пути к маршруту и игре хранятся относительно файла проекта
  и абсолютными. **Открыть проект** (Ctrl+Shift+O) сам открывает маршрут и каталог игры.
- **Файл → Экспорт сценария** (Ctrl+E) пишет в `routes/<маршрут>/scenarios/<имя>/`:
  `main.lua` (`setTime`, `TrainData` + `setTrain` для каждого поезда), `README.md` (описание и таблица
  поездов с расписанием), `timetable/<поезд>.xml`. Имя сценария — латиница, цифры, `_`, `-`.
- Состав поезда: если он совпадает с готовым из `cfg/trains` — берётся он; иначе (отредактированный
  или собранный) в `cfg/trains` создаётся `<сценарий>-<поезд>.xml` (одинаковые составы — один файл;
  повторный экспорт не дублирует). Существующие файлы составов не перезаписываются.
- Расписание: первая станция без `ArrivalTime`, последняя без `DepartureTime` (как в примерах игры);
  проезд без остановки — равные прибытие и отправление; `ApproachTraj`/`RemovalTraj` — траектории пути
  непосредственно перед и после траектории станции (по ним автопилот строит маршруты приёма и отправления).
- Перед записью проверяются: имена поездов (уникальны), пересечения, тупик, состав и модули; предупреждения —
  бот без автопилота, график без бота, отправление по графику раньше начала игры.
  Начало игры по умолчанию — за 3 мин до первого отправления.
- Каталог существующего сценария заменяется только с галочкой; в нём перезаписываются лишь `main.lua`,
  `README.md` и расписания поездов (чужие файлы не удаляются).

Пока нет: запрос о несохранённых изменениях при закрытии.

### События: триггеры и действия (вкладка «События сценария»)

Событие = триггер + список действий. Всё записывается в `main.lua` после поездов и сохраняется в проекте.

Триггеры: в заданное время суток (`setTimeTrigger("ЧЧ:ММ:СС")`); через время после начала игры
(`"+ЧЧ:ММ:СС"`); траектория занята / освобождена любым или заданным поездом
(`setOnTrajBusyTrigger`, `setOnTrajFreeByTrainTrigger` …) с необязательной выдержкой
(`setPostEventTimeTrigger`); автоматический пропуск поездов (`setAutoApproachTrigger`).

Действия: поездной и маневровый маршрут (`buildTrainRoute`, `buildShuntingRoute`), стрелки по маршруту,
стрелка в плюс/минус, открыть поездной/маневровый/пригласительный сигнал, закрыть сигнал,
переименовать и развернуть поезд.

Траектории можно вводить с подсказкой по имени или указывать щелчком по карте («На карте…»); стрелки и
поезда выбираются из списков. Проверки: пустые поля и отсутствие действий блокируют экспорт; неизвестные
траектории/стрелки/поезда, время раньше начала игры и маршруты, которых по топологии нет (проверка
поиском пути в обоих вариантах входа), — предупреждения.

### Импорт существующих сценариев (Файл → Импортировать сценарий…)

Читается каталог сценария (`main.lua`, `timetable/*.xml`, `README.md`):

- `setTime`, поезда (`TrainData` + `setTrain`; состав берётся из `cfg/trains`), расписания
  (в том числе `ApproachTraj`/`RemovalTraj`, платформы, `IsVisible` — они сохраняются как есть);
- события: `setTimeTrigger`, `setOnTraj…Trigger`, `setAutoApproachTrigger` с готовыми
  `action…(…)`, с функциями-обёртками из прямых вызовов (`buildTrainRoute`, `switchFwd`, `openSignal` …)
  и с задержкой (`setPostEventTimeTrigger` внутри функции). Значения вида `train1.traj`,
  `train1.dir` и константы `local x = "…"` подставляются;
- всё остальное (свои функции с логикой, `setTrigger`, поезда с неизвестным составом или траекторией,
  нестандартные вызовы) сохраняется **как есть** в проекте и записывается в `main.lua` при экспорте:
  объявления — до поездов, прочий код — после событий. Имена переменных поездов остаются прежними,
  чтобы сохранённый код продолжал на них ссылаться. Функции и константы, которые полностью
  заменены событиями и больше нигде не используются, не дублируются;
- комментарий перед оператором становится названием события.

Ограничения: лексический разбор, а не полный интерпретатор Lua — сложные выражения в аргументах
остаются кодом как есть. Движение импортированных расписаний не участвует в проверке пересечений поездов
(у них нет рассчитанной траектории), пока график не пересоздан в редакторе. Комментарии внутри
распознанных блоков (кроме заголовка события) не сохраняются.

Все 9 сценариев из каталога `scenarios` маршрута «полигон» импортируются, а Lua после экспорта разбирается
повторно с тем же результатом (проверка в тесте при заданном `RRS_ROUTE_DIR`).

## Сборка (Windows, MinGW)

Нужны Qt 6 (компонент MinGW 64-bit) и CMake 3.20+. Из каталога проекта:

    cmake -S . -B build -G "MinGW Makefiles" -DCMAKE_PREFIX_PATH=C:/Qt/6.x.x/mingw_64
    cmake --build build
    build\rrs-scenario-editor.exe

Чтобы запустить не из Qt Creator, рядом с программой нужны библиотеки Qt:

    windeployqt build\rrs-scenario-editor.exe

## Сборка (Linux)

    sudo apt install qt6-base-dev cmake g++
    cmake -S . -B build
    cmake --build build

## Использование

Файл → Открыть маршрут… и выбрать каталог маршрута, то есть `routes/<имя маршрута>` из папки игры
(внутри должна быть папка `topology`). Либо передать этот каталог аргументом командной строки.

## Тесты

    cmake -S . -B build -DRRS_ROUTE_DIR=<путь к routes/experimental-polygon_v2.0>
    cmake --build build
    ctest --test-dir build --output-on-failure

Без `RRS_ROUTE_DIR` проверки на реальном маршруте пропускаются, остальные тесты работают на
синтетическом маршруте. Тест отрисовки запускается без дисплея (`QT_QPA_PLATFORM=offscreen`);
если задать каталог `RSE_SHOT_DIR`, он сохранит в него картинки схемы.

## Особенности данных RRS, учтённых в коде

- Длина траектории считается в 3D (с высотой) и склеивает точки ближе 1 см, как это делает симулятор.
- Траектории `bwd*` примыкают к стрелке концом, `fwd*` — началом; `fwdMinusTrajReversed` — концом
  со стороны «вперёд». Проверено на всех 279 стрелках полигона: разрывов нет.
- В данных стандартного маршрута «Испытательный полигон 2.0» есть ссылки на несуществующие траектории
  (например `track_a_p2k`, `track_c_n-per`). Редактор показывает их как замечания.
- Конфиг состава `vl60pk-1543-poezd2.xml` объявлен как UTF-8, но содержит комментарий в cp1251.
  Редактор читает такие файлы терпимо (битые символы заменяются) и сообщает о кодировке.
- Готовые составы `VL60k-poezd2342`, `vl60pk-1543-T33_15` и `vl60pk-1543-poezd2` указывают
  `ModuleDir` = `vl60k` или `vl60pk`, тогда как CMake игры собирает эти модули в `modules/vl60`.
  Если в вашей установленной игре нет таких каталогов, редактор предупредит, что симулятор эти составы
  не загрузит (проверено только по исходникам, на собранной игре сверьте).
- Признака «туда/обратно» в файлах траекторий нет: все траектории идут от начала к концу. Правильное
  направление пути выводится из светофоров в `topology.xml`: литера `SignalLiterBwd` — светофор со стороны
  «назад», ведущий поезда вперёд через стрелку, `SignalLiterFwd` — со стороны «вперёд», ведущий назад.
  Учитываются только стрелки, где задана одна из литер (проходные светофоры с обеими литерами направления
  не дают) и только поездные светофоры: маневровые (`М7`, `НМ3`, `ЧМ5`) пропускаются. Светофор с буквой «Д»
  в конце (`ЧД`, `НД`) — выход на неправильный путь, поэтому правильным считается обратное направление.
  Найденное направление переносится по цепочке траекторий через простые стыки (по одной траектории
  с каждой стороны). Проверено на двухпутных перегонах ростовского узла (оба пути получают встречные
  направления). Это вывод из данных, в игре его стоит сверить.
- Флаг `auto` в сценарии включает автоведение, только если у первой или последней единицы состава есть
  модуль автопилота. Панель показывает такие составы пометкой «авто».

## Перенос и перетаскивание локомотива (этап 8)

- **Диалог «Положение…»**: список «Путевая точка» переносит состав в точки из `waypoints.conf`
  маршрута (путь, координата и направление берутся из точки); поле «Путь» (с поиском)
  переносит на любую другую траекторию — голова встаёт в середину пути по правильному направлению.
- **Мышь**: выбранный состав можно взять мышью и перетащить по путям и участкам. Под курсором
  рисуется «призрак» состава (красный — если не умещается или пересекается). При отпускании
  голова встаёт в точку под курсором; на другом пути направление выбирается по ходу пути.
  Щелчок по другому составу выбирает его. Пересечение с другим составом и тупик блокируют перенос.
- После переноса график состава сбрасывается (маршрут изменился).
- При закрытии окна с несохранёнными изменениями проекта спрашивается подтверждение.

## Проверка графиков и продолжение поезда (этап 9)

### Проверка графиков сценария («Проверка → Проверить графики сценария…», F7)

Все расписания сценария прогоняются по общей сетке времени (шаг 10 с): положение каждого поезда
(с учётом длины состава и стрелок) сравнивается с остальными. Находит:

- **ошибки**: два поезда на одном месте пути, встречное движение на одном пути, поезд приходит
  туда, где стоит или будет стоять другой; отправление раньше начала сценария; прибытие раньше
  отправления; продолжение отправляется раньше сцепки;
- **риски**: интервал между движущимися поездами меньше 30 м (возможен затор: второй встанет на
  светофоре), подход к стоящему поезду ближе 10 м (в игре они сцепятся автоматически), график есть,
  а бот выключен;
- **заметки**: график загружен из файла и не имеет расчёта движения (пересечения с ним не
  проверяются - пересчитайте график в редакторе).

Окно остаётся открытым и обновляется при правках; двойной щелчок выбирает поезд и показывает его
на карте. Те же проблемы попадают в предупреждения при экспорте. Это оценка по расчётным точкам, а не
симуляция: реальные поезда могут идти чуть иначе.

### Продолжение: локомотив подходит к вагонам, цепляет их и едет дальше

1. Поставьте вагоны (стоящий состав без бота) и локомотив с графиком, у которого конечная точка
   стоит вплотную к вагонам (ближе 10 м, не на них).
2. Выберите локомотив в списке → **«Продолжение…»**: укажите вагоны, имя нового поезда и задержку
   после прибытия (сцепка, опробование тормозов).
3. В списке появится строка «↪ имя»: у неё нет места на путях, положение и состав вычисляются
   сами (локомотив повернут на месте + вагоны; голова - бывший хвост локомотива). Задайте ей график
   обычной кнопкой **«График…»** - расчёт идёт для всего нового состава.
4. При экспорте: поезд-продолжение в `main.lua` не создаётся (`setTrain` нет), пишется
   `timetable/<имя>.xml`, а в момент «прибытие + задержка» - событие `renameTrain("локомотив", "имя")`
   и `reverseTrain("имя")`. Локомотив ставится в `main.lua` раньше вагонов.

Почему так (по исходникам симулятора): при сцепке остаётся поезд с меньшим индексом (порядок
`setTrain`) и сохраняет своё имя; `renameTrain` заново читает `timetable/<новое имя>.xml` для вагонов
с автопилотом; после сцепки голова поезда - дальний конец вагонов, поэтому для движения обратно
головой вперёд нужен `reverseTrain`. **В игре это ещё не проверено.** Если локомотив или вагоны
меняются, продолжение пересчитывается; если сдвинулась точка прибытия - его график сбрасывается.
Удаление локомотива или вагонов удаляет и продолжение.

## Маршруты по правилам игры (этап 10)

- **Подход и уход** станций больше не берутся «соседями по пути». Станция определяется по именам
  траекторий (`track_<станция>_…` - станция, `track_<А>-<Б>_…`, `routeN_…` - перегон) и по ролям
  светофоров (`line/entr/rout/exit/shnt` по модели светофора). Подход - перегонная траектория
  перед той, что заканчивается входным светофором; уход - первая перегонная траектория после
  выходного. На реальных графиках Ростов - Тимашевская и Волгодонская - Сальск результат
  совпадает с игровым либо отличается выбором параллельного пути перегона.
- Автопилот ищет маршрут поиском в ширину по наименьшему числу траекторий и в одном направлении
  на весь график; `simulateAutopilot` (`scenario/stationroute.h`) выполняет график «на бумаге»
  и находит случаи, когда светофор не откроется.
- **Путь станции** выбирается в окне графика (столбец «Путь станции»): маршрут перестраивается
  через выбранный путь, результат сразу виден на карте.
- **Окно графика не модальное**: карта доступна (панорама, масштаб, выбор конца пути щелчком),
  маршрут на карте обновляется при каждом изменении.
- **Будущий поезд** (флажок в положении поезда): в сценарий пишется только `timetable/<имя>.xml`,
  на карте в начале сценария поезда нет. Имя должно совпасть с тем, которое поезд получит
  в игре (например, при переименовании после сцепки).
- Не проверено в самой игре. Будущие поезда пока не участвуют в проверке пересечений.

## Триггеры по графикам и очерёдность (этап 11)

- При экспорте (флажок в окне экспорта, по умолчанию включён) редактор сам создаёт триггеры
  маршрутов по расписаниям: приём на станцию (поезд занял подход), отправление (по времени или
  при проходе без остановки). Для ботов маршруты строит автопилот, триггеры им нужны только там,
  где важна очерёдность.
- **Категория поезда** (скорый → пассажирский → пригородный → грузовой → резервом) задаётся в
  положении поезда, по умолчанию определяется по номеру (`scenario/autotriggers.cpp`). Если
  графики поездов спорят за один путь (окно 5 мин), маршрут поезда низшей категории строится
  только после освобождения общего пути поездом высшей категории, а в расписании подход/уход
  этой станции очищается, чтобы автопилот не занял путь первым. Если по графику младший идёт
  раньше старшего, выводится предупреждение.
- Игра приоритетов не знает; это реализовано триггерами «путь освобождён поездом». Порядок
  категорий и нумерацию стоит сверить с вашими правилами. Не проверено в самой игре.

### Светофоры по времени графика (этап 13)

Маршруты строятся не только когда поезд занял подход, но и по времени графика: приём - за минуту
до входа поезда на подход, отправление - за 10 с до времени отправления (проход без остановки -
за 30 с до прохода), с повторами через 45 и 120 с, если путь был занят. Маршрут открывает станционные
светофоры и переводит стрелки; на станции с остановкой выходной светофор остаётся закрытым до
времени отправления. Где путь спорят поезда разных категорий, маршрут младшего ждёт старшего.
Триггеры лежат в main.lua между маркерами `-- [rse-auto begin]` и `-- [rse-auto end]`, при импорте
игнорируются и создаются заново при каждом экспорте.

### Подход и уход по светофорам, длинные маршруты, конфликты маршрутов (этап 14)

- Станции определяются **по светофорам**, а не по именам траекторий (в маршрутах из редактора карты
  все траектории называются `routeN_NNNN_NNNN`): входной светофор открывает зону, первый выходной
  за ним закрывает. Подход - перед линейными светофорами, ведущими ко входному, уход - сразу за
  выходным.
- Если на перегоне между станциями есть стрелки с ответвлением, уход продлевается до подхода
  следующей станции: единый маршрут переводит все стрелки и открывает станционные светофоры.
- Маршруты поездов, которые редактор строит триггерами, учитываются при проверке графиков:
  поезда одной категории, чьи маршруты одновременно занимают одну траекторию, дают замечание
  «Маршруты поездов … одновременно занимают …» (F7 и экспорт).

### Весь перегон открывается сразу (этап 15)

Маршруты строятся не по времени каждой станции, а по перегонам между остановками: в момент
отправления со станции остановки (за 10 с до него) подряд, через 3 с, строятся маршруты всех
следующих станций до следующей остановки (приём и отправление каждой), с повторами через 60 и 180 с.
Выходной светофор станции остановки открывается ко времени отправления. Занятые пути для проверки
конфликтов и очерёдности считаются с момента построения маршрута, а не с прохода поезда.

### Поезда друг за другом (этап 16)

Игра занимает траектории маршрута до прохода поезда и не строит через занятую маршрутом
траекторию другой маршрут. Поэтому маршрут следующего поезда по тому же пути строится, когда
идущий впереди освободит общие траектории (триггер «путь освобождён поездом»). Это действует
и для поездов одной категории: первым идёт тот, кто раньше по графику.

## Этап 31 — верное направление путей и двусторонние пути

### Исследование (по трём реальным маршрутам: Волгодонская—Сальск, Ростовский узел, Ростов—Горячий Ключ)

- Прежний алгоритм определял направление лишь у 50.8% / 75.9% / 52.8% траекторий. Корень
  проблемы: конфликт литер ±1 (светофоры в обе стороны) занулял траекторию, а перенос по
  стыкам затем назначал ей направление от первого соседа — цепочка перегона разрывалась
  «половина туда, половина обратно» (зависимость от порядка переноса).
- Разбор данных показал: конфликт литер — в основном норма (однопутные перегоны с двусторонней
  автоблокировкой, станционные пути приёма в обе стороны), а не ошибка данных. `RelPosVector`
  светофоров бесполезен (константы/нули), имена траекторий — ненадёжны (конвенции авторов
  различаются).
- Правило РЖД подтверждено по ПТЭ/ИДП: движение на двухпутных линиях правостороннее
  (правильный путь — правый, встречные слева); у пары параллельных путей направления
  противоположны, и правильное направление пути — то, при котором сосед оказывается слева.

### Алгоритм v2 (`Route::calcPathDirections`, route.cpp)

- Уровень 1: литеры стрелок (как раньше; «Д» инвертирует, маневровые не учитываются).
- Уровень 2: пары параллельных путей (межосевое 3.2–7.5 м, почти параллельны, близкой длины,
  длина > 80 м) — правостороннее правило РЖД; пара отбрасывается целиком, если однозначный
  светофор любого члена ей противоречит (соседние станционные пути бывают одного направления).
  Проверка на трёх маршрутах: согласие принятых пар с однозначными светофорами — 100%
  (32/0, 90/0, 66/0); направление получило 15/22/53 траектории, у которых алгоритм ошибался.
- Уровень 3: перенос по простым стыкам; конфликтным траекториям направление переноса не
  назначается.
- Уровень 4: конфликт литер без разрешающей пары — двусторонний путь: `pathDirection()`
  возвращает `Both` (enum `PathDirection { Unknown, Fwd, Bwd, Both }` в route-data.h,
  `path_both_` в Route). Контракт `orientation()` сохранён (−1/0/+1).
- Исправление из тестов: `QRectF::intersects` считает вырожденный габарит (прямой участок —
  нулевая высота bbox) непересекающимся; перекрытие габаритов проверяется по диапазонам
  координат явно.

### Карта и диалоги

- `MapWidget`: стрелки направления по `pathDirection()` — синие «туда», оранжевые «обратно»,
  **зелёные в обе стороны** для двусторонних путей (отдельная серия стрелок навстречу),
  серые точки — только «неизвестно». Ховер повторяет стиль.
- Диалог расстановки поезда: для двустороннего пути — «двусторонний путь (движение в обе
  стороны)» вместо «направление не определено»; предупреждение «голова против хода пути» на
  двусторонних путях не выдаётся (поезд вправе смотреть в любую сторону).

### Тесты

- `test-route`: фикстура `buildDirectionRoute` (двухпутный перегон без литер, пара станционных
  путей одного направления с чётными выходными, конфликт литер без пары, конфликт в середине
  цепочки со стыками) + тесты `directionDoubleTrackByPair`, `directionPairRejectedBySignals`,

- `realRouteDirectionStats`: статистика покрытия на реальных маршрутах (переменная окружения

## Этап 33 — совместимость с RRS 1.10 (составы из других источников)

### Анализ ветки v1.10.0-devel (сравнение с 1.9.4 по исходникам)

- Главный механизм: **модуль ПЕ назначается в конфиге самой единицы** (секция Vehicle,
  поля Module и ModuleDir). Симулятор 1.10 (`simulator/train/src/train.cpp`) читает его
  приоритетно; поля Module/ModuleDir конфига состава - запасной источник (обратная
  совместимость с 1.9.4, где они обязательны).
- Формат топологии (topology.xml, *.traj) не менялся (`Topology::load` - только потоковый
  параметр завершения); формат расписания (Timetable XML) и Lua-интерфейс триггеров
  не менялись; изменения vehicle.cpp - клиентские сигналы, редактор не затрагивают.

### Редактор: двойная совместимость

- Каталог (`VehicleCatalog`): из конфига единицы читается собственный модуль
  (`VehicleConfigData::ownModule`); в группах составов модуль единицы перекрывает
  указание в составе - так же, как решает симулятор 1.10.
- Составы нового формата (группа Vehicle без Module) загружаются, если модуль назначен
  единице; замечание о пропуске секции - только когда модуля нет ни в составе, ни в
  конфиге единицы.
- `resolveModules()`: источник `ModuleSource::OwnConfig` - абсолютный приоритет (выше
  ручных привязок, которые для таких единиц не нужны и в игре 1.10 не применились бы).
- Экспорт не менялся: конфиг поезда по-прежнему содержит Module/ModuleDir (нужны 1.9.4),
  при этом значения согласованы с приоритетом 1.10 - обе версии загружают одно и то же.
- Панель подвижного состава показывает источник привязки «из конфига единицы (RRS 1.10)».
- Тест `ownConfigModuleWins110` (test-catalog): перекрытие указания в составе, чтение
  1.10-состава без Module в группе.

## Этап 34 — окно графика: удаление/вставка станций, устойчивость к конфликту, размер окна

### Правки по обратной связи (окно «График»)

- **Изменяемый размер окна.** Минимальный размер 700x460, геометрия запоминается между
  открытиями (QSettings ui/timetableGeometry, сохраняется в деструкторе - при любом
  способе закрытия).
- **Удаление станции красным крестом.** Новый столбец «Удалить»: у каждой промежуточной
  строки красный крест, крайние строки (начало/конец) не удаляются. Убранная станция
  исчезает из таблицы целиком и не возвращается при пересчётах (в отличие от галочки
  «В графике»). Список убранных хранится у поезда (`timetableHidden`, JSON-ключ
  timetable_hidden) и переживает повторные открытия.
- **Вставка станции зелёным «+».** При наведении мыши на границу между строками
  появляется зелёный кружок с «+» (TimetableTable отслеживает мышь у краёв строк).
  Щелчок вставляет пустую строку с выпадающим списком станций; после выбора станция
  получает настройки из состояния, «км» и путь станции. Добавленные станции, не лежащие
  на пути плана, попадают в расписание как ExtraStop (привязка к ближайшей точке пути,
  при отступе больше 400 м - предупреждение); хранятся у поезда (`timetableExtra`,
  JSON-ключ timetable_extra). Повторное добавление станции, убранной крестом,
  возвращает её в график.
- **Конфликт пути не сбрасывает график.** Если путь перестроить не удалось (например,
  до выбранного пути станции доехать физически нельзя), прежний график остаётся на
  экране: таблица, времена и сводка без изменений, в замечаниях - сообщение с именем
  станции-виновника (TripPlan::failedVia - какая точка маршрута не достижима), строка
  станции подсвечивается лёгким красным. Таблица при этом не перезаполняется - выбор
  пользователя в комбобоксах остаётся виден. Кнопка «Применить» оставляет прежний,
  корректный график.
- **Прокрутка не сбрасывается.** При перестроении таблицы (смена пути станции,
  закрепления, конечной точки) прокрутка возвращается к строке, которая была первой
  видимой, либо к прежней позиции - окно больше не перепрыгивает в начало.
- **Подчёркивание всей ячейки времени.** Прибытие/отправление подчёркиваются линией
  во всю ширину ячейки (ClockCellDelegate у колонок), а не только текст; шрифтовое
  подчёркивание убрано.
- Исправлено накопление замечаний: список предупреждений перечитывается при каждом
  пересчёте (warnings_->clear() перед добавлением), а не дополняется.

### Технические детали

- `computeTrip()`: слияние `TripOptions::extraStops` в строки по положению на пути
  (сорт, защита от строк ближе 30 м друг к другу); `buildTripPlan()` запоминает
  `failedVia` - индекс недостижимой точки (vias + конечная).
- `TimetableDialog`: столбец ColRemove, `row_station_` кодирует добавленные строки
  значениями -10-k (параллельный список row_added_ с именем, s и отступом), ручные
  времена работают и для добавленных строк; вставка строки - с блокировкой сигналов
  таблицы (иначе itemChanged на недостроенной строке разбирал пустое имя как правку).

### Проверка

- Новые тесты: `removeAndInsertStations` (крест, «+», возврат станции, повторное
  открытие), `planFailureKeepsTimetable` (недостижимый путь станции: график и времена
  на месте, предупреждение с именем станции, красная подсветка, восстановление),

## Этап 35 — светофоры для поездов без автоведения: расписание как у разработчиков игры

### Проблема

В сценариях, собранных редактором, у поездов с выключенным автоведением (`auto = false`) светофоры
открывались только скриптовыми `buildTrainRoute` из main.lua. В сценариях разработчиков игры
(«Волгодонская—Сальск», «Ростовский узел», «Ростов—Горячий Ключ») поезд без автоведения едет по
графику, и светофоры открываются сами — сценарий проходится.

### Причина (по исходникам игры RRS, maisvendoo/RRS)

- Расписание `timetable/<имя>.xml` игра грузит для **каждого** поезда (`Model::slotUpdateTrainTimetable`),
  независимо от флага `auto`. Флаг `auto` — это только автозапуск/автоведение (`Model::buildAutostartQueue`).
- Автопилот-устройство в локомотиве (`Autopilot::slotRouteBuildRequest`) строит маршрут приёма по
  `ApproachTraj` и отправления по `RemovalTraj` для любого поезда с графиком: подход — при входе на
  траекторию приближения, отправление — по времени графика; занятые пути он обходит повторами запроса.
- Генератор редактора **стирал** эти поля из расписания там, где планировал событие очерёдности
  (`clearApproach`/`clearRemoval` в экспорте, комментарий «автопилот его строить не должен») — у
  G-101 из 12 станций оставалось 3 поля. Движок терял механизм открытия светофоров, и всё держалось
  на скриптовых событиях.

### Решение

- Экспорт всегда записывает `ApproachTraj`/`RemovalTraj` для всех станций всех поездов, как в
  сценариях разработчиков (`src/scenario/export.cpp`); механика `clearApproach`/`clearRemoval`
  удалена (`src/scenario/export.h`, `src/scenario/autotriggers.cpp/.h`). События очерёдности
  остаются страховкой и для порядка пропуска: маршрут через занятый блок движок всё равно не
  построит, повторный `buildTrainRoute` безопасен.
- Панель «Автособытия» показывает ровно то, что попадёт в экспорт: события для всех поездов с
  расписанием (`forBots = true` в `refreshAutoEvents`), а не только для поездов без автоведения.
- Регрессионный тест `timetableKeepsApproachWithOrdering` (test-export): два поезда одной категории
  на одном пути со сдвигом в минуту — события очерёдности создаются, но подход/уход в расписании
  сохраняются.

### Проверка

- Полный прогон 14 наборов тестов зелёный, включая новый.
- E2E на реальных маршрутах (утилита scripts/e2e-export.cpp): импорт сценария разработчика
  `Train_6813` («Волгодонская—Сальск», `auto = false`, без событий) и экспорт редактором — в
  расписании 10 станций, 9 подходов и 8 уходов (у разработчиков 16 полей), значения траекторий
  совпадают с оригиналом. Реэкспорт сценария «Daily-Rostov2»: у G-101 было 0 подходов и 3 ухода,
  стало 10 и 10; суммарно по пяти поездам 43 подхода и 36 уходов на 49 станций.
